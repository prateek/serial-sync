The correction trial exposed an importer detail: an in-place overwrite can be skipped when the directory modification time does not change. The adapter uses atomic replacement, then waits for the scan and verifies the downloaded hash. Do not substitute an in-place copy or overlapping filesystem watcher.

The notification follow-up verified the current public library URL returns BookOrbit over HTTPS and sent one new `Serial-sync link check` using the existing adapter's payload format. Its gateway again reported one notified device; the user confirmed it opened only exe.dev. This rules out the original test's timing before the HTTPS access change as the explanation for the fresh failure. Shelley's [actual gateway payload](https://github.com/boldsoftware/shelley/blob/10f4ce93795cc75841fcba02da042414155ceffe/server/server.go#L2346) nests conversation routing under `data`; it does not establish support for the adapter's top-level `url` or arbitrary website navigation. No speculative conversation IDs or action types were added. Private probe evidence is `deployment/notification-link-check.json`.

The user subscribed to the unguessable hosted ntfy topic, then confirmed that `Serial-sync phone link test` arrived and opened BookOrbit. The Docker probe used the existing `Publisher.notify` method with temporary state and verified the exact `click` URL through API readback, without consuming the real chapter outbox. The private probe waits for its own uniquely titled message because an immediate latest-message read returned an earlier test. Evidence is in `deployment/notification-ntfy-phone-check.json`; `deployment/notification_ntfy_probe.py` is the rerunnable probe. The [ntfy iOS v1.7.0 notification handler](https://github.com/binwiederhier/ntfy-ios/blob/893bae9cce985c6272ac70f9e75874bf8fc67a27/ntfy/App/AppDelegate.swift#L152) also confirms the click handling.

The live Docker image read back `kind = ntfy` with announcements enabled; the hourly timer remained active. The phone report confirms delivery and navigation, but does not separately establish whether the device was locked at delivery.

The migration does not copy every possible reader preference. The source had one viewer-preference record; reader preferences were not migrated. Source annotations and bookmarks were empty. The existing database and file backup remain available. Arbitrary volume regrouping and multi-user progress migration are outside this deployed personal-library path.

New publications carry current metadata choices. Existing editions retain their previous metadata unless explicitly rebuilt; the Steamforged pilot was the only historical metadata rebuild applied during rollout. The 38 EPUB series continue using stable singles. The seven manual/preserve review queues and unresolved discovery candidates retain their prior handling. Validation commands completed: Docker `go test ./...`, demo `setup check`, fixture publication and no-op runs, real EPUB2 and EPUB3 publication, focused artwork-cache/navigation tests, and nine Python adapter tests. ## Recovery boundary

The initial migration retained Grimmory's stopped application, running database, and files as a temporary rollback path. The user subsequently requested removal of all Grimmory resources from the VM. Do not use an old `docker start grimmory` command as the recovery procedure. The infrastructure runbook in `prateek/infra`, `hosts/prateek-books/`, owns current inventories, pinned Compose definitions, private backup/restore commands, and recovery-test evidence.

The original Grimmory migration was rehearsed from a SQL dump and copied library. Those private off-VM snapshots remain historical recovery evidence. They do not contain progress or chapters added in BookOrbit after cutover. Recover the current service from a consistent BookOrbit database dump, library files, app state, serial-sync configuration/catalog/captures/receipts, and private credentials. Retain the historical storage aliases until their references are explicitly migrated.
